We are starting a NEW POST-PRELIMINARY DEVELOPMENT CYCLE for the AIC 2026 system.

The goal is NOT merely to edit the existing technical report.

The goal is:

1. freeze the current historical baseline;
2. identify the highest-value technical failures;
3. improve the system using evidence-driven engineering;
4. evaluate improvements under a controlled protocol;
5. freeze a reproducible improved version;
6. then produce a NEW technical report that clearly distinguishes:
   - competition-time system/workflow;
   - post-preliminary improvements.

The existing technical report and all previous evidence audits remain historical sources of truth.

Do NOT rewrite competition history to match the new code.

PHASE 2 — FAILURE-DRIVEN DIAGNOSIS
==================================================

Do NOT immediately implement new ideas.

First analyze existing evaluation data, traces, query-level results and failure records.

Classify failures for:

KIS
Q&A
TRAKE

Suggested taxonomy:

- query-understanding failure;
- translation/caption drift;
- retrieval miss;
- correct video but poor frame localization;
- relevant candidate ranked too low;
- fusion failure;
- duplicate/shot-allocation issue;
- OCR/ASR/object-signal failure;
- temporal reasoning failure;
- insufficient evidence;
- incorrect Q&A answer;
- refusal/sentinel behavior;
- TRAKE missing-event interpolation;
- latency bottleneck;
- mapping/export failure;
- runtime/configuration failure.

Do not force every failure into this taxonomy if evidence suggests a better classification.

For each major failure class estimate:

- frequency if measurable;
- severity;
- affected task;
- likely root cause;
- confidence in root cause;
- possible technical interventions.

Then rank candidate improvements by:

IMPACT × EVIDENCE × IMPLEMENTATION COST × REGRESSION RISK.

Output a prioritized list of at most 5 primary improvement targets.

==================================================
PHASE 4 — IMPLEMENTATION
==================================================

After approval, implement improvements incrementally.

Rules:

- prefer small, attributable changes;
- write/update focused tests;
- do not silently change scorer/evaluation protocol;
- preserve old configurations where needed for baseline comparison;
- do not modify historical submission artifacts;
- do not fabricate missing ground truth;
- do not tune against data then later call that same data unbiased.

Each meaningful change must have an experiment ID or documented run.

For every implementation keep:

- commit;
- config;
- model;
- data/index version;
- command;
- result;
- query-level deltas;
- regressions.

If an experiment regresses important metrics:

analyze → rollback or revise.

Do not keep a change just because implementation effort was high.

==================================================
PHASE 5 — CONTROLLED EVALUATION
==================================================

Evaluate baseline and improved versions using the SAME protocol.

Where evidence allows, measure:

KIS:
- R@1;
- R@5;
- R@20;
- R@50;
- R@100;
- aggregate score;
- frame localization quality if ground truth supports it.

Q&A:
- retrieval/evidence quality;
- answer correctness where verified ground truth exists;
- invalid/refusal rate;
- unsupported-answer failure rate if measurable;
- latency.

TRAKE:
- event retrieval;
- temporal ordering;
- evidence-backed vs interpolated positions;
- correctness where verified ground truth exists;
- latency.

Engineering:
- crash rate;
- mapping violations;
- export violations;
- preflight failures;
- reproducibility.

Report query-level wins/losses, not only aggregate metrics.

For any major gain, check whether improvement came from:

- broader candidate pool;
- reranking;
- query processing;
- model change;
- data/index change;
- evaluation leakage;
- accidental configuration difference.

Perform ablation when attribution matters.

==================================================
EVALUATION SAFETY
==================================================

Distinguish:

TRAIN/TUNING DATA

DIAGNOSTIC DATA

VALIDATION DATA

HELD-OUT DATA

COMPETITION DATA

A set used repeatedly for design decisions must not later be described as unbiased evaluation.

If no truly independent set exists, say so.

Do not fabricate one.

==================================================
REGRESSION GATE
==================================================

Before accepting the improved system:

- run focused tests;
- run full applicable test suite;
- run preflight;
- run clean evaluation;
- inspect major query-level regressions;
- verify mapping/export;
- verify task routing;
- verify model/config identities.

A new system is not “better” merely because one aggregate metric increased.

Document meaningful regressions.
